# План: бонусы при проигрыше в раннере для уровней электростанции 1–3

## 1. Контекст

Есть 3D‑раннер (`GameRunView.vue` + backend `GameRun*View`), в котором пользователь:

- запускает забег, обнуляя `storage` и фиксируя его стартовое значение в `UserProfile.energy_run_start_storage`;
- в процессе забега собирает энергию (`energyCollected`);
- в конце видит экран результатов (win/lose) и может нажать «Забрать».

Сейчас при **проигрыше** количество энергии, которое пользователь в итоге забирает, зависит **только** от уровня инженеров (белые/золотые + синие электрики) и **не зависит** от уровня электростанции.

Новая бизнес‑логика:

- Для **электростанций 1 и 2 уровня** при проигрыше некоторое количество раз подряд пользователь должен забирать **100 %** собранной энергии.
- Для **электростанции 3 уровня** — некоторое количество раз подряд пользователь забирает **50 %** собранной энергии.
- Количество таких «льготных» проигрышей и сами проценты должны настраиваться в админке Django по адресу `/admpan15513/core/runnerconfig/` (модель `RunnerConfig`).
- После исчерпания лимита по уровню станции включается **текущая** логика (по инженерам).
- Для уровней электростанции **4–10** логика **не меняется**.

Правки в этом документе описывают только анализ и план изменений; реализацию в коде можно сделать отдельным шагом.

## 2. Текущая логика проигрыша

### 2.1. Фронтенд: `GameRunView.vue`

Ключевые элементы:

- Экран результатов (`win/lose`) — шаблон в `GameRunView.vue`, блок `game-over-card`.
- Тип завершения:
  - `showGameOver: ref(false)`
  - `gameOverType: ref('lose') // 'win' | 'lose'`
- Собранная энергия для отображения:
  - `savedEnergyCollectedForModal: ref(0)` — фиксируется:
    - при смерти (3‑я потеря жизни), до остановки игрового цикла;
    - в `endGame()` — до/после вызова `gameRun.completeRun()`, но **не перезаписывается меньшим значением**;
  - `completedRunData: ref(null)` — результат `gameRun.completeRun()` или локальный fallback.
- Компонозабег `useGameRun()` (`src/composables/useGameRun.js`) держит:
  - `energyCollected` — сколько реально собрал игрок;
  - `startStorage` — сохранённый `storage` на момент старта забега;
  - массив `collectedEnergyPoints` для серверной валидации.

#### Отрисовка результатов проигрыша

В шаблоне (`GameRunView.vue`):

- Отображение собранной энергии:

```vue
{{ formatEnergy(displayedEnergyCollected, true) }} / {{ formatEnergy(gameRun.startStorage?.value ?? gameRun.currentStorage?.value ?? 0) }} kW
```

- Информация по инженерам:

- `whiteEngineerLevel`, `goldEngineerLevel` — уровни белых/золотых инженеров;
- `whiteEngineerSavedPercent`, `goldEngineerBonusPercent` — проценты сохранения от `app.stations.eng_configs` (`saved_percent_on_lose` для соответствующих уровней);
- `effectiveSavedPercentOnLose = white + gold`.

Суммарный процент сохранения при проигрыше показывается так:

```vue
<span class="game-over-result-value">
  {{ formatPercent(effectiveSavedPercentOnLose) }}
</span>
```

`claimableEnergy` (энергия «к забору»):

- сначала берёт `completedRunData.value.energy_gained` (то, что вернул сервер), если оно есть;
- если нет — локально пересчитывает:

```js
const pct = effectiveSavedPercentOnLose.value
const electricsBonus = (app?.user?.electrics_expires && new Date(app.user.electrics_expires) > new Date()) ? 2 : 0
return (collected * (pct + electricsBonus)) / 100
```

То есть **фронт при фоллбэке тоже опирается только на инженеров + синих электриков.**

### 2.2. Бэкенд: `GameRunCompleteView` и `GameRunClaimView`

#### Источники данных

- `UserProfile` (`edit/core/models.py`):
  - `energy_run_last_started_at` — время последнего старта забега;
  - `energy_run_start_storage` — `storage` на момент старта (максимум собираемой энергии);
  - поля по перегреву/тренировкам и т.д.;
  - методы:
    - `get_station_level()` — возвращает индекс текущего типа станции (0–9) из списка:

```python
STATION_LEVELS = [
    "Boiler house",          # 0 → «1 уровень станции»
    "Coal power plant",      # 1 → «2 уровень»
    "Thermal power plant",   # 2 → «3 уровень»
    "Geothermal power plant",
    "Nuclear power plant",
    "Thermonuclear power plant",
    "Dyson Sphere",
    "Neutron star",
    "Antimatter",
    "Galactic core",
]
```

#### Расчёт процента сохранения при проигрыше

Функция `calculate_saved_percent_on_lose(user_profile, now=None)` в `edit/core/views.py`:

- берёт:
  - `engineer_level` и `past_engineer_level` из `UserProfile`;
  - из `EngineerConfig` (таблица конфигов инженеров) поля `saved_percent_on_lose` для разных уровней, включая 49‑й;
  - наличие активных синих электриков (`user_profile.electrics_expires > now`) даёт +2 %.
- логика:
  - делит общий прогресс на «белых» и «золотых» инженеров по трём случаям (описаны в докстринге функции);
  - вычисляет:
    - процент белых: `white_percent` по уровню `white_level`;
    - процент золотых: `gold_percent = max(0, total_percent - level49_percent)`;
  - суммирует: `saved_percent = white_percent + gold_percent`;
  - при наличии электриков добавляет +2 %;
  - ограничивает итог максимумом 100 %.

#### Где применяется сохранение при проигрыше

1. `GameRunCompleteView`:

```python
if is_win:
    final_energy = energy_collected
else:
    saved_percent = calculate_saved_percent_on_lose(user_profile, now)
    final_energy = energy_collected * (saved_percent / 100)
```

- эта `final_energy` не начисляется, а возвращается как `energy_gained` в ответе `game-run-complete/`:

```python
return Response({
    "success": True,
    "message": "Run completed successfully. Click 'Claim' to receive energy.",
    "energy_collected": float(energy_collected),
    "energy_gained": float(final_energy),  # сколько получит при "Забрать"
    "is_win": is_win,
    ...
})
```

2. `GameRunClaimView`:

- повторно валидирует данные;
- считает `final_energy` **по той же формуле**:

```python
if is_win:
    final_energy = energy_collected
else:
    saved_percent = calculate_saved_percent_on_lose(user_profile, now)
    final_energy = energy_collected * (saved_percent / 100)
```

- начисляет `final_energy` в:
  - `UserProfile.energy`;
  - `WalletInfo.kw_amount`;
  - `GlobalSpendStats.total_energy_accumulated`;
  - реферальные бонусы;
- обнуляет `energy_run_start_storage` и ставит `energy_run_claimed_at = now` (идемпотентность).

**Итого сейчас:** при проигрыше и на фронте, и на бэкенде процент сохранения энергии зависит **исключительно от инженеров** (и синих электриков), уровень станции не учитывается.

## 3. Требуемое новое поведение при проигрыше

Формулировка требований:

1. **Станции 1 и 2 уровня**
   - При проигрыше пользователь временно получает **100 %** собранной за забег энергии.
   - Для каждой из этих станций действует свой независимый лимит по количеству проигрышей:
     - пример: для 1‑го уровня — 200 проигрышей с 100 % возвратом;
     - для 2‑го уровня — также 200 проигрышей с 100 % возвратом.
   - После исчерпания лимита по конкретному уровню станции:
     - при дальнейшем проигрыше на этом уровне станции применяется **старая логика** (процент по инженерам).

2. **Станция 3 уровня**
   - При проигрыше пользователь временно получает **50 %** собранной энергии.
   - Действует независимый лимит по количеству проигрышей (пример: 100 раз).
   - После исчерпания лимита:
     - дальше используется обычная логика по инженерам.

3. **Станции 4–10 уровней**
   - Поведение **полностью сохраняется**: процент при проигрыше зависит только от инженеров (как сейчас).

4. **Конфигурируемость через админку**
   - В `/admpan15513/core/runnerconfig/` (модель `RunnerConfig`) должны быть настраиваемыми:
     - процент сохранения энергии при проигрыше для:
       - станции 1 уровня;
       - станции 2 уровня;
       - станции 3 уровня;
     - максимальное количество «льготных» проигрышей (лимит) для каждого из этих уровней.
   - Значения по умолчанию:
     - уровень 1: процент 100 %, лимит 200;
     - уровень 2: процент 100 %, лимит 200;
     - уровень 3: процент 50 %, лимит 100.

5. **Граница применения**
   - Если льготный режим **активен** (лимит не исчерпан), то:
     - процент инженеров **игнорируется**;
     - опционально — можно игнорировать и бонус синих электриков, чтобы не превышать 100 %.
   - Если льготный режим **исчерпан** или отключён конфигом:
     - используется текущий `calculate_saved_percent_on_lose()` **без изменений**.

## 4. Изменения в модели RunnerConfig (админка)

Сейчас `RunnerConfig` (`edit/core/models.py`) содержит:

- `stars_per_kw`;
- `max_training_runs_per_hour`;
- параметры генерации поинтов и скорости забега.

### 4.1. Новые поля в RunnerConfig

Предлагаем расширить модель так (псевдокод — для понимания структуры, реализация будет через миграции):

```python
class RunnerConfig(models.Model):
    """Конфигурация для раннера"""

    # ... существующие поля ...

    # --- Льготный процент при проигрыше для станций 1–3 уровня ---

    lose_percent_station_level_1 = models.FloatField(
        default=100,
        help_text="Процент собранной энергии при проигрыше для станции 1 уровня"
    )
    lose_percent_station_level_2 = models.FloatField(
        default=100,
        help_text="Процент собранной энергии при проигрыше для станции 2 уровня"
    )
    lose_percent_station_level_3 = models.FloatField(
        default=50,
        help_text="Процент собранной энергии при проигрыше для станции 3 уровня"
    )

    # --- Лимиты количества льготных проигрышей (на пользователя) ---

    lose_max_uses_station_level_1 = models.IntegerField(
        default=200,
        help_text="Сколько раз пользователь может получить льготный процент на 1 уровне станции"
    )
    lose_max_uses_station_level_2 = models.IntegerField(
        default=200,
        help_text="Сколько раз пользователь может получить льготный процент на 2 уровне станции"
    )
    lose_max_uses_station_level_3 = models.IntegerField(
        default=100,
        help_text="Сколько раз пользователь может получить льготный процент на 3 уровне станции"
    )
```

Семантика полей:

- проценты — глобальные для всех пользователей;
- лимиты — максимальное количество льготных проигрышей **на одного пользователя** для соответствующего уровня станции.

При смене значений в админке:

- новые проценты/лимиты применяются к последующим проигрышам;
- уже израсходованные пользователем попытки не «откатываются» (счётчики хранятся отдельно в `UserProfile`).

## 5. Отслеживание лимитов на пользователя (UserProfile)

Чтобы лимит был не глобальным, а **персональным**, нужны дополнительные поля в `UserProfile`:

```python
class UserProfile(models.Model):
    # ... существующие поля ...

    # Льготные проигрыши раннера по уровням станции
    runner_lose_uses_level_1 = models.IntegerField(
        default=0,
        help_text="Сколько льготных проигрышей уже было на станции 1 уровня"
    )
    runner_lose_uses_level_2 = models.IntegerField(
        default=0,
        help_text="Сколько льготных проигрышей уже было на станции 2 уровня"
    )
    runner_lose_uses_level_3 = models.IntegerField(
        default=0,
        help_text="Сколько льготных проигрышей уже было на станции 3 уровня"
    )
```

Интерпретация:

- `runner_lose_uses_level_N` — **счётчик уже использованных** льготных проигрышей на уровне станции `N`;
- текущий лимит для пользователя на уровне `N` вычисляется как:

```python
remaining_uses_N = max(0, config.lose_max_uses_station_level_N - user_profile.runner_lose_uses_level_N)
```

При каждом проигрыше на уровне `N`:

- если используется льготный процент, инкрементируем `runner_lose_uses_level_N` на 1;
- если льготный процент не применяется (лимит закончился / уровень станции > 3 / конфиг не задан) — счётчик не меняется.

Вопрос миграции:

- существующим пользователям поля инициализируются `0`, что означает «все льготные попытки ещё доступны».
- сами миграции для добавления этих полей (`makemigrations` / `migrate`) выполняются отдельно вручную на бэкенде и не входят в рамки этого плана.

## 6. Новая серверная логика расчёта процента при проигрыше

Чтобы не дублировать код в `GameRunCompleteView` и `GameRunClaimView`, логичнее вынести общую логику в отдельный helper.

### 6.1. Новый helper

Псевдокод функции (можно разместить рядом с `calculate_saved_percent_on_lose`):

```python
def calculate_saved_percent_with_station_bonus(user_profile, now=None):
    """
    Возвращает процент сохранения энергии при проигрыше с учётом:
    - уровня станции (1–3) и льготных лимитов;
    - текущей логики инженеров (fallback).
    """
    from django.utils import timezone
    if now is None:
        now = timezone.now()

    # 0. Получаем конфиг раннера
    config = RunnerConfig.objects.first()
    if not config:
        # Нет конфига → просто используем старую логику по инженерам
        return calculate_saved_percent_on_lose(user_profile, now)

    # 1. Определяем уровень станции (1–10)
    try:
        station_level = user_profile.get_station_level() + 1  # 1..10
    except ValueError:
        # station_type вне списка — безопасный fallback
        return calculate_saved_percent_on_lose(user_profile, now)

    # 2. Для уровней 4–10 ничего не меняем
    if station_level >= 4:
        return calculate_saved_percent_on_lose(user_profile, now)

    # 3. Для уровней 1–3 — льготная логика, если есть оставшиеся попытки
    if station_level == 1:
        max_uses = config.lose_max_uses_station_level_1
        used = user_profile.runner_lose_uses_level_1
        bonus_pct = config.lose_percent_station_level_1
        field_name = "runner_lose_uses_level_1"
    elif station_level == 2:
        max_uses = config.lose_max_uses_station_level_2
        used = user_profile.runner_lose_uses_level_2
        bonus_pct = config.lose_percent_station_level_2
        field_name = "runner_lose_uses_level_2"
    else:  # station_level == 3
        max_uses = config.lose_max_uses_station_level_3
        used = user_profile.runner_lose_uses_level_3
        bonus_pct = config.lose_percent_station_level_3
        field_name = "runner_lose_uses_level_3"

    # Если лимит отключен (<= 0) или уже исчерпан — fallback на инженеров
    if max_uses <= 0 or used >= max_uses:
        return calculate_saved_percent_on_lose(user_profile, now)

    # Здесь мы применяем льготный процент и должны инкрементировать счётчик.
    # ВАЖНО: инкремент делаем там, где реально начисляем энергию (GameRunClaimView),
    # а в GameRunCompleteView можно только вернуть процент без обновления счётчика.

    return max(0, min(bonus_pct, 100))
```

**Замечание:** чтобы не ломать идемпотентность и не дублировать обновление счётчиков:

- в `GameRunCompleteView` можно вызывать helper **в режиме read‑only** (без инкремента счётчиков) — только для того, чтобы отдать корректный `energy_gained` в ответ;
- в `GameRunClaimView`:
  - после вычисления процента и перед начислением энергии — инкрементировать соответствующий `runner_lose_uses_level_N` (через `F()`‑выражение);
  - при повторном claim (когда `energy_run_start_storage is None` и сработала идемпотентность) счётчики **не трогать**.

### 6.2. Применение helper в существующих view

В обоих местах, где сейчас вызывается `calculate_saved_percent_on_lose(user_profile, now)`, нужно перейти на:

```python
saved_percent = calculate_saved_percent_with_station_bonus(user_profile, now)
final_energy = energy_collected * (saved_percent / 100)
```

При этом:

- сама функция `calculate_saved_percent_on_lose` остаётся без изменений, хранит текущую бизнес‑логику инженеров;
- новая функция оборачивает её и добавляет станционную часть для уровней 1–3.

## 7. Как лимиты должны вести себя при смене уровня станции

Сценарии:

1. Пользователь на станции 1 уровня, несколько раз проиграл:
   - `runner_lose_uses_level_1` растёт до лимита;
   - при апгрейде до уровня 2 эти данные не теряются (если вдруг будет даунгрейд в будущем).

2. Пользователь переходит на станцию 2 уровня:
   - начинает использовать лимит `lose_max_uses_station_level_2`, счётчик `runner_lose_uses_level_2`.

3. При переходе на уровни 4+:
   - льготная логика не применяется;
   - счётчики могут остаться в профиле «на всякий случай» (не мешают).

4. Если в будущем появится откат станции:
   - при возвращении на уровень 1/2/3 используются уже накопленные значения `runner_lose_uses_level_N`, лимит не «обнуляется».

Такое поведение простое и предсказуемое: «один пользователь — фиксированное количество льготных проигрышей на каждый низкий уровень станции, независимо от времени и апгрейдов».

## 8. Влияние на фронтенд и一致ность UI

После внедрения серверной логики:

- поле `energy_gained` в ответах `game-run-complete/` и `game-run-claim/` уже будет учитывать:
  - льготные проценты станций 1–3;
  - или обычный процент по инженерам (для станций 4–10 или после исчерпания лимитов).
- `GameRunView.vue` в `claimableEnergy` в нормальном случае использует именно `completedRunData.energy_gained`, т.е. **фактическое значение с сервера**, и оно будет корректным.

Чтобы UI был консистентным и прозрачно показывал «помощь новичкам», предлагается следующая конкретная схема для модалки проигрыша в `GameRunView.vue`.

### 8.1. Состояние «льготный режим активен» (есть лимит, станция 1–3 уровня)

Условие: на бэке для текущего забега был применён станционный бонус (уровень 1–3, лимит ещё не исчерпан).

- **Новая строка «Помощь новичкам»**:
  - Добавить отдельный ряд над строками по инженерам:
  - Текст: `Помощь новичкам: X%`, где `X` — фактический процент льготного сохранения для текущего уровня станции.
  - Источник `X`:
    - либо отдельное поле из ответа бэка (например, `station_bonus_percent` или общий `saved_percent_effective`);
    - либо вычисление на фронте как `energy_gained / displayedEnergyCollected * 100`, если `energy_gained > 0` и считается именно по станционному бонусу.

- **Строка по белому инженеру**:
  - Вместо того, чтобы показывать его вклад как часть фактического сохранения, показываем его как «потенциал»:
  - Текст по смыслу: «Белый инженер мог бы сохранить: Y%».
  - Число `Y` берётся из уже существующего `whiteEngineerSavedPercent` (по `eng_configs`), т.е. это тот процент, который действовал бы **без помощи новичкам**.
  - Реализуется либо отдельным ключом локализации (`game.run_result_saved_by_level_potential`), либо через текущий текст + суффикс «(мог бы сохранить)».

- **Строка «Всего сохранено»**:
  - В этом состоянии итоговый процент должен совпадать с тем, что реально применил бэк:
    - если в конфиге `lose_percent_station_level_N = 100`, то показываем `Всего сохранено 100%`;
    - если админ поменял на 80 — показываем `Всего сохранено 80%` и т.д.
  - Источник процента:
    - либо отдельное поле бэка (`saved_percent_effective`/`energy_run_saved_percent`);
    - либо, если есть и `energy_gained`, и `energy_collected` (или `displayedEnergyCollected`), считать как `round(energy_gained / collected * 100)`.

- **Строка по золотому инженеру**:
  - Аналогично белому можно оставить как «потенциал» (если нужно), или скрыть при активной «Помощи новичкам» — зависит от финального UX‑решения.

Важный момент: при активной «Помощи новичкам» **итоговая сумма процентов в UI должна совпадать с реально начисленной энергией**, а инженерные проценты в этом состоянии трактуем как «что было бы без помощи».

### 8.2. Состояние «льготный режим не активен» (лимит исчерпан или станция 4–10)

- Строка «Помощь новичкам» **не показывается**.
- Строки по белому/золотому инженеру и «Всего сохранено» работают как сейчас:
  - `whiteEngineerSavedPercent`, `goldEngineerBonusPercent`, `effectiveSavedPercentOnLose` считаются только по инженерам (плюс синие электрики).
- `Всего сохранено` можно оставить как `effectiveSavedPercentOnLose`, либо унифицировать с подходом из 8.1, считая процент как `energy_gained / collected * 100`, если нужны абсолютно точные данные.

Таким образом, пользователь в модалке проигрыша явно видит:

- отдельную строку **«Помощь новичкам: X%»**, пока действует лимит по текущему уровню станции;
- сколько **могли бы сохранить инженеры** (`Y%`), если бы не было помощи;
- **«Всего сохранено Z%»**, где `Z` всегда согласовано с реальным начислением энергии на бэке.

## 9. Резюме по задаче

- **Сейчас:** при проигрыше сохранение энергии определяется исключительно уровнем инженеров (белых/золотых) и синими электриками; уровень электростанции и лимиты по проигрышам не учитываются.
- **Требуется:** добавить для станций уровней 1–3 льготный режим при проигрыше (100 %/100 %/50 % энергии) с настраиваемыми процентами и лимитами в `RunnerConfig`; для уровней 4–10 всё оставить как есть.
- **Архитектура:** расширить `RunnerConfig` и `UserProfile`, добавить helper `calculate_saved_percent_with_station_bonus`, который оборачивает существующую `calculate_saved_percent_on_lose`, и использовать его в `GameRunCompleteView`/`GameRunClaimView`.
- **После реализации:** фактическое начисление будет соответствовать новой бизнес‑логике, а фронтенд можно доработать, чтобы корректно отображать процент сохранения с учётом уровня станции и лимитов.
