### Анализ использования TON API во фронтенде

**Цель**: понять, как фронт сейчас использует TON API (`tonapi.io` и связанные вызовы), и что будет, если ограничиться **1 запросом/секунду** (глобально или на инстанс), не поломав игровые/финансовые механики.

---

### 1. Клиенты и источники данных TON

- **`axios.config.js`**
  - `tonapi` — `https://tonapi.io/v2/` с Bearer-токеном.
  - `toncenter` — `https://toncenter.com/api/v3/` (HTTP-клиент, во фронте напрямую не используется).
- **`@ton/ton` + `TonClient`**
  - В `WalletView.vue`, `RentScreen.vue`, `StakingScreen.vue` создаются `TonClient` с `endpoint: 'https://toncenter.com/api/v2/jsonRPC'` и отдельным API key.
  - Эти вызовы идут **не через `tonapi.io`**, а через toncenter JSON-RPC.

Вывод: под ограничение **1 RPS tonapi.io** попадают только запросы через `tonapi` из `axios.config.js`. Все, что идёт через `TonClient` и `toncenter`, живёт в своих лимитах.

---

### 2. Где и как используется `tonapi`

#### 2.1. `src/stores/app.js`

- `init()`:
  - `tonapi.get('rates?tokens=fBTC,kW,TON&currencies=usd')`
  - Вызывается при старте приложения / инициализации `useAppStore`.
  - Частота: **единичный запрос на init**, максимум несколько раз за сессию (при перезапуске сторы).
- Влияние при снижении частоты:
  - Если курсы станут реже обновляться — пользователю просто покажутся слегка устаревшие USD-цены в `WalletView`.
  - На внутренние игровые расчёты (энергия, майнинг, ренту, стейкинг) этот запрос **не влияет** — всё это идёт через ваш backend (`host`).

#### 2.2. `src/views/WalletView.vue`

- Функция `startInfoUpdate()`:
  1. `await app.initUser()` — только backend, TON тут не трогается.
  2. `tonapi.get(\`accounts/${connectedAddressString.value}\`)`
     - Обновляет `app.tonBalance`.
  3. `await delay(2000)`
  4. `tonapi.get(\`accounts/${connectedAddressString.value}/jettons\`)`
     - Обновляет `app.jettons`.
  5. `setTimeout(() => startInfoUpdate(), 5000)`
- Эффективная частота:
  - 2 запроса к `tonapi` примерно каждые **7 секунд** ⇒ ~**0.28 RPS на одного активного пользователя на экране Wallet**.
- Логика/UX:
  - Баланс TON и jetton-ов обновляется “почти real-time”.
  - Ошибки просто логируются, критической завязки геймплея на эти данные нет — это витрина кошелька.

#### 2.3. `src/components/investor/RentScreen.vue`

Функция `updateRent()`:

1. **Инициализация ASIC-коллекций (редко, но жирно по RPS)**:
   - Если `localStorage` не содержит `all_asics`:
     - `tonapi.get('nfts/collections/{collection1Addr}')`
     - `tonapi.get('nfts/collections/{collection2Addr}')`
     - Затем серия запросов:
       - `tonapi.get('nfts/collections/{collection1Addr}/items?offset=...')` по страницам (шаг 1000).
       - `tonapi.get('nfts/collections/{collection2Addr}/items?offset=...')` по страницам.
   - Это пачка **из десятков+ запросов** единоразово при первом заходе на экран и пустом кэше.
   - Результат сохраняется в `localStorage` как сильно ужатый список (`address`, `name`, `attributes`), чтобы не дергать tonapi каждый раз.

2. **Пользовательские NFT по коллекциям**:
   - При наличии `connectedAddressString.value`:
     - `tonapi.get('accounts/<addr>/nfts?collection=collection1Addr')`
     - `tonapi.get('accounts/<addr>/nfts?collection=collection2Addr')`
   - Выполняется **каждый цикл** `updateRent`.

3. **Цикл опроса**:
   - В конце:
     - `timeoutId = setTimeout(() => updateRent(), 3000)`
   - Итого на одного юзера на вкладке Rent:
     - **2 запроса к `accounts/.../nfts` каждые 3 секунды** ⇒ ~**0.67 RPS**.
     - Плюс иногда burst на инициализацию коллекций (см. п.1).

4. **Влияние на механику**:
   - Эти данные используются для:
     - отображения списка собственных ASIC NFT для аренды/рента;
     - расчетов, какие NFT уже в распоряжении пользователя и какие доступны на аренду;
     - фильтрации и отображения асиков в интерфейсе.
   - Если уменьшить частоту:
     - Пользователь будет видеть **чуть более старый снимок** своих ASIC (может, на несколько секунд/десятков секунд).
     - Логика backend-а (создание/завершение рент, проверка владения) не ломается — она всё равно проверяет всё на сервере.
     - Единственный возможный UX-эффект: аренда/возврат NFT может не сразу отразиться в списке на фронте.

#### 2.4. `src/components/investor/StakingScreen.vue`

Функция `updateStaking()`:

1. `await app.initStaking()` — только backend.
2. `tonapi.get(\`accounts/${connectedAddressString.value}/jettons\`)`
   - Обновляет `app.jettons` для расчёта доступного `myTBTC`.
3. В конце:
   - `timeoutId = setTimeout(() => updateStaking(), 3000)`

Частота: **1 запрос к `tonapi` каждые 3 секунды** ⇒ ~**0.33 RPS** на активного пользователя на экране Staking.

Влияние при снижении частоты:
- Если обновлять реже:
  - `myTBTC` будет лагать по факту реального баланса кошелька.
  - При создании стейкинга всё равно идёт:
    - on-chain транзакция через TonConnect;
    - проверка и запись через ваш backend (`host.post('create-user-staking/')`).
  - То есть ошибка “не тот баланс” на фронте критична только для UX (кнопка `MAX`, отображаемый остаток), а не для целостности данных.

#### 2.5. `src/composables/useTonApiPolling.js`

- Готовый, но **фактически не используемый** сейчас хук.
- Логика:
  - `initialInterval = 2000`, `maxInterval = 30000`, экспоненциальный backoff, остановка при `document.hidden`, замедление при неактивности пользователя.
  - Идеально подходит, чтобы **снизить общее количество запросов**, т.к. агрессивно “удлиняет” интервалы при отсутствии изменений.

---

### 3. Суммарная нагрузка на TON API по экранам

Если смотреть **на одного активного пользователя**:

- **WalletView**: ~0.28 RPS (`accounts`, `jettons`).
- **RentScreen**:
  - steady-state: ~0.67 RPS (`accounts/.../nfts` две коллекции).
  - холодный старт без кэша: burst по коллекциям (`collections`, `items`).
- **StakingScreen**: ~0.33 RPS (`accounts/.../jettons`).
- **App init**: единичный `rates`-запрос.

Если эти экраны могут быть открыты одновременно (в пределах одной сессии/таба, но у реальных юзеров — параллельно), то выйти на **глобальный лимит 1 RPS** при нескольких пользователях очень просто:

- 2–3 пользователя, активно сидящих в Rent/Staking/Wallet, уже дают **суммарно 2–4 RPS**.

---

### 4. Что будет, если “жестко” урезать до 1 RPS на tonapi

Если понимать лимит как **проекта в целом** (а не per-IP/per-client):

- При сохранении существующих частот опроса:
  - любое реальное количество одновременных пользователей > 1 периодически будет упираться в лимит.
  - Начнут сыпаться ошибки/429 от tonapi.
- Как это отразится на логике:
  - **Wallet**:
    - Баланс TON/jettons иногда не обновится; пользователь увидит старые цифры, но серверная логика кошелька и внутриигровой баланс не ломаются.
  - **Rent**:
    - Может “подвисать” отображение актуальных ASIC NFT и доступных рент.
    - В худшем случае фронт не покажет свежее изменение, пока не пройдет удачный запрос.
    - Операции ренты как таковые защищены backend-ом (он проверит реальные владения/лимиты).
  - **Staking**:
    - Аналогично: отображаемый доступный fBTC может устаревать, `MAX` будет брать не совсем актуальное число.
    - Но транзакция и запись стейка валидируются на backend-е, поэтому логика не развалится.

Вывод: **механики и инварианты проекта (майнинг, рента, стейкинг, кошелёк) не завязаны критично на tonapi**. Это скорее сервис для витринных данных и client-side удобства. Урезание RPS повлияет в основном на UX/real-time-ощущение.

### 5. Возможные стратегии снижения количества запросов

Ниже — варианты, которые позволят приблизиться к 1 RPS (или хотя бы сильно снизить общий трафик), **без ломки логики**.

#### 5.1. Поднятие интервалов опроса

- **WalletView**:
  - Сейчас: 2 запроса за ~7 секунд.
  - Безболезненно:
    - Увеличить задержку перед `setTimeout` до 15–30 секунд.
    - Либо вызывать обновление только:
      - при открытии экрана;
      - по кнопке “Обновить”;
      - при явных событиях (успешная транзакция через TonConnect, изменение адреса).

- **StakingScreen**:
  - Сейчас: 1 запрос каждые 3 секунды.
  - Можно:
    - сделать опрос раз в 20–30 секунд;
    - либо дергать tonapi только после успешных stake/unstake-операций и при открытии вкладки.

- **RentScreen**:
  - Сейчас: 2 запроса каждые 3 секунды (плюс burst при инициализации).
  - Без потери логики:
    - опрос раз в 15–30 секунд;
    - отдельная кнопка “Обновить мои NFT / аренду”;
    - отменить фоновый постоянный опрос, оставив синхронизацию по явным действиям (зашел на экран, только что заключил/завершил рент и т.п.).

#### 5.2. Агрессивное кэширование и дедупликация

- **Уже есть**:
  - `localStorage`-кэш `all_asics` с данными коллекций — хорошее решение, но инициализационный burst лучше либо:
    - переносить на backend (см. 5.4),
    - либо делать ленивой подгрузкой (порциями по 1 странице/секунду), если строго нужен 1 RPS.
- **Можно добавить**:
  - Кэш балансов и jetton-ов по адресу пользователя в `localStorage`/Pinia с TTL (напр. 30–60 сек).
  - Перед каждым `tonapi.get('accounts/...')` проверять, нет ли свежих данных — и не дёргать сеть.

#### 5.3. Использование уже написанного `useTonApiPolling`

Сейчас `useTonApiPolling` нигде не подключён, но:

- Он уже умеет:
  - backoff по неизменяющимся данным;
  - остановку при `document.hidden`;
  - замедление при неактивности пользователя.
- Стратегия:
  - Переписать Wallet/Rent/Staking с ручного `setTimeout` на `useTonApiPolling`.
  - Параметрами `initialInterval`/`maxInterval` загнать реальный средний RPS до нужного уровня.

#### 5.4. Прокси через backend (серверный “агрегатор” TON API)

Самый “чистый” путь, если реально хочешь **строгий 1 RPS наружу**:

- Подход:
  - Фронт перестает ходить в `https://tonapi.io` напрямую.
  - Все запросы идут к вашему backend-у, например:
    - `/ton/accounts/:address`
    - `/ton/accounts/:address/jettons`
    - `/ton/accounts/:address/nfts`
    - `/ton/rates`
  - Backend:
    - имеет глобальный лимитер (1 RPS к tonapi для всего проекта);
    - кэширует ответы по ключу (адрес + тип запроса) на 10–30 сек;
    - раздаёт кэш многим фронтам/юзерам.

- Эффект:
  - При 100 активных юзерах:
    - фронт может опрашивать backend хоть раз в 2–3 секунды;
    - backend всё равно бьёт по tonapi максимум 1 раз в TTL (например, раз в 10–30 секунд) по каждому типу ресурса.
  - Логика не ломается: backend всё равно авторитетный источник для ваших игровых операций; tonapi становится “read-only витриной”.

#### 5.5. Переход на альтернативные источники (тонцентр / собственный индексатор)

- Часть функционала (NFT, jettons, балансы) уже дублируется через `TonClient` + toncenter.
- Потенциальные шаги:
  - Перевести всё, что сейчас идёт через `tonapi`, на:
    - либо toncenter (с отдельным тарифом/лимитами),
    - либо собственный индексатор (если/когда он будет).
- Это уже архитектурное решение, но оно снимает зависимость от конкретного тарифа tonapi.

### 6. Итог по влиянию на механику при снижении RPS

1. **Критические инварианты проекта** (майнинг, начисление, рента, стейкинг, лимиты, блокировки) живут на backend-е и on-chain, а не в tonapi.
2. **Фронтовые вызовы tonapi**:
   - используются для:
     - витринных балансов (TON, fBTC, kW в кошельке);
     - списка NFT/jettons пользователя;
     - курсов токенов в USD;
     - инициализации локального справочника ASIC.
   - могут быть безопасно **урезаны по частоте** (вплоть до десятков секунд/минут) без риска поломать экономику.
3. **Реальные риски при 1 RPS без архитектурных изменений**:
   - деградация UX (не сразу обновились балансы/списки);
   - ошибки 429 от tonapi, которые нужно аккуратно логировать и fallback-ить на кэш.
4. **Реально достижимый сценарий**:
   - Без изменения архитектуры (только тюнинг интервалов + кэш):
     - можно сильно снизить нагрузку (в разы),
     - но строгий глобальный 1 RPS при >1 активном пользователе всё равно сомнителен.
   - С backend-прокси и кэшированием:
     - **можно** делать хоть 1 запрос/сек к tonapi на проект,
     - фронт при этом продолжит опрашивать ваш backend с текущими или чуть увеличенными интервалами,
     - логика и механики останутся без изменений, пострадает только “живость” фронта в пределах секунд/десятков секунд.

### 7. Что я бы предложил как следующий шаг

1. **Быстрый win без бэкенда**:
   - Увеличить интервалы:
     - Wallet: хотя бы до 15–30 секунд.
     - Rent: до 15–30 секунд, плюс кнопка ручного обновления.
     - Staking: до 20–30 секунд, плюс ручное обновление после операций.
   - Включить `useTonApiPolling` для всех повторяющихся запросов вместо ручных `setTimeout`.
2. **Среднесрочно**:
   - Вынести `accounts/*`, `jettons`, `nfts`, `rates` на backend-прокси с кэшем и глобальным rate limiter.
3. **Долгосрочно**:
   - Рассмотреть переход на toncenter/свой индексатор для heavy-нагрузки (NFT-коллекции, массовые выборки).

При таком подходе можно **агрессивно урезать реальное количество запросов к tonapi** до уровня бесплатного тарифа, не ломая механику и только чуть ухудшив “онлайновость” отображаемых данных.
